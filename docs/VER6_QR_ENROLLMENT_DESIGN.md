# Ver.6 QR初回登録 — 安全な実装仕様（未実装）

## 前提
- GitHub Pages は公開静的サイト。秘密鍵・管理者権限・QR検証を置かない。
- Supabase Auth / RLS を維持。スタッフ識別はQRの文字列だけでは確定しない。
- 既存Ver.5 `index.html` とVer.6 `ver6-preview.html` は変更しない。
- 架空データで検証し、実運用前に権限・監査・失効テストを実施する。

## 提案フロー
1. 管理者が既存の認証でサインインし、管理者権限をサーバー側で確認。
2. 管理者が対象スタッフを指定して招待を発行。暗号学的乱数で生成した十分長いトークンの**ハッシュだけ**をDBに保存し、有効期限（例10分）、未使用、対象ユーザーID、発行者を記録。発行操作は監査ログに記録。
3. QRにはHTTPSの登録URLとワンタイムトークンのみを含める。Supabase secret/service_role、既存セッション、固定パスワードは含めない。URLの漏洩対策として登録ページはreferrer-policy:no-referrer、外部解析・外部リンクなし、トークンのログ記録なし。
4. スタッフが端末でURLを開き、本人確認を別経路で実施する（例：管理者による対面確認と短い確認コードの照合）。QRだけを持つ第三者が登録できない設計。
5. Supabase Edge Functionが本人確認・期限・未使用・スタッフ状態を検証し、DBトランザクションで一回限りの使用を確定。競合時は一方のみ成功。セッション発行はSupabase Authの正式なサーバー側フローで行い、独自JWTやservice_roleキーのブラウザー配布は禁止。
6. 端末にログイン状態を保存するが、サーバー側で端末単位の有効状態を確認。すべての権限付き操作で無効端末を拒否する。単なるUI非表示では不可。
7. 紛失・機種変更時は管理者が旧端末を失効させ、既存セッション/refresh tokenも失効できるようにし、再登録QRを発行。アクセストークンの残存有効期間も考慮し、DB側の端末失効チェックで即時拒否する。
8. 発行・登録成功/失敗・期限切れ・再発行・端末失効を監査ログに記録。トークンや認証情報はログに残さない。

## 実装前に確認する事項
- Supabase Authでスタッフごとのセッション発行と端末単位失効をどう実現するか（公式機能・制約を検証）。
- `profiles` と `auth.users` の対応、スタッフの事前登録方法。
- Edge Functionの認証、DBテーブル・RPC・RLS・既存の `add_receipt` / `change_receipt` / `cancel_receipt` の認可経路。
- 管理者が確認する本人確認方法とQR有効期限。
- デバイス識別をブラウザ指紋に依存しない方式にすること。

## 合格条件
- 未使用QRは本人確認後1回だけ成功、同時利用でも2回成功しない。
- 期限切れ・改ざん・再利用・他スタッフ向けQRは拒否。
- 非管理者によるQR発行・端末失効はサーバーで拒否。
- 端末失効後、旧端末の閲覧・発注・受領RPCは拒否。
- 端末変更後、新端末だけが使える。
- RLS、監査ログ、既存受領機能、Ver.5の動作に回帰なし。

**状態：設計のみ。QR登録・端末失効・Edge Functionは未実装。**

## 確定した運用（2026-10-29）
- **管理者とスタッフが同じ場所で対面登録する**運用を採用する。
- 管理者が対象スタッフを選択し、本人を対面確認してから招待を発行する。
- スタッフ本人が自分の端末でQRを読み取る。管理者は画面上で対象者と登録完了を照合する。
- QRを読み取るだけで本人認証完了とは扱わない。QRの盗撮・転送・先取り登録に対抗するため、別経路の本人確認とサーバー側の一回限りの承認が必要。
- **本人確認の具体的な実装とSupabase Authのセッション発行方式は検証前**。それらが成立するまで実際の登録機能は公開しない。
- 機種変更・紛失時は管理者の対面確認を再度行い、旧端末を失効させた後に新しい招待を発行する。
