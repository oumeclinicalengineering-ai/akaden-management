## 確認できた事実
1. 現行プレビューは `supabase.auth.signInWithPassword` を使う。QRログインは未実装。
2. `enter()` は `profiles` から `display_name,role,active` を取得するが、これは**UI表示・入口のチェック**であり、RLSの安全性の証明にはならない。
3. 受領履歴の修正・取消ボタンは `created_by===user.id || profile.role==='admin'` で表示制御される。**RPC側が同じ認可を実施するか未検証**。
4. `add_receipt` / `change_receipt` / `cancel_receipt` の実際のSQL定義は、このリポジトリからは検証できていない。
5. QR招待発行Edge Functionはログインユーザーの `getUser` と管理者プロフィールをサーバー側で照合するコードを持つが、未デプロイ・未テスト。ブラウザーOriginを拒否するため、現時点で画面からは呼べない。
6. 招待消費RPCは使用済み・期限切れを原子的に防止する案だが、本人確認の承認やAuthセッションの発行は行わない。

## ブロッカー（解消まで本番接続しない）
- Supabase管理画面から**既存RLSポリシーと3つの受領RPCのSQL定義**を確認し、管理者/本人/無効スタッフの操作権限をサーバー側で検証する。
- Supabase Authの公式なパスワードレス認証手段（OTP/メールリンク/WebAuthn等）と、管理者対面承認の組み合わせを設計する。**QRトークンをSupabase Authの代わりに使わない**。
- 管理者がスタッフを対面確認した事実を、特定の登録申請に紐づけてサーバーに記録する。現行HTMLのチェックボックスは承認にならない。
- 登録端末の有効性を、全ての読み取りRLSと書き込みRPCで検証する。Authのサインアウトだけで即時失効したと判断しない。
